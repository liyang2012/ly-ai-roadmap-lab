## 🔑 核心知识点

### 1. Hybrid Search：向量 + BM25 = 取长补短

**为什么单一检索不够？**

| 问题类型 | 向量检索 | BM25 | 示例 |
|----------|---------|------|------|
| 语义相似 | ✅ 优秀 | ❌ 弱 | "坏了"="故障" |
| 精确关键词 | ❌ 不稳定 | ✅ 强 | "X100"型号 |
| 同义词 | ✅ 好 | ❌ 差 | "免邮"="包邮" |
| 缩写/代码 | ⚠️ 一般 | ✅ 好 | "R50"→"R50 Lite" |

**RRF (Reciprocal Rank Fusion) 融合算法：**

```
RRF_score(d) = α × 1/(k + rank_vec) + (1-α) × 1/(k + rank_bm25)
```

- `k = 60`（平滑参数，避免除零）
- `α = 0.5`（两种检索各占一半）
- 在两个列表中都靠前的文档得分最高
- RRF 是无监督的，不需要训练

**关键参数 α：**
- `α=1.0`：纯向量检索（等于 Week 1）
- `α=0.5`：混合（默认推荐）
- `α=0.0`：纯 BM25

### 2. Reranking：精排的最后一步

**Bi-Encoder vs Cross-Encoder：**

```
Bi-Encoder（向量检索）：
  Query → [Encoder] → vec_q ────┐
  文档   → [Encoder] → vec_d ────┤ → 相似度 → 分数
  速度：快（文档向量可预计算）
  
Cross-Encoder（重排序）：
  (Query, Doc) → [Encoder] → 分数
  速度：慢（每对都要重新计算）
  精度：高（query 和 doc 同时编码，交互更充分）
```

**Pipeline 设计模式：**
1. 向量 / Hybrid 检索 → 20 篇候选（快速初筛）
2. Reranker → Top-5（精排）
3. LLM Generation（基于最终结果）

**生产环境选择：**
- 小规模（<1000 文档）：Hybrid + LLM Reranker 足够
- 中等规模（1K-100K）：Hybrid + BGE-Reranker-v2-minicpm
- 大规模（>100K）：向量初筛 + 分布式 Reranker

### 3. Query 改写：让检索更聪明

**三种改写策略：**

| 策略 | 方法 | 效果 | 适用场景 |
|------|------|------|---------|
| 关键词提取 | LLM 提取核心关键词 | 去噪，聚焦 | 精确查询 |
| 同义词扩展 | LLM 生成多个同义表达 | 增加命中率 | 口语化问题 |
| 子问题拆解 | LLM 拆解复杂问题 | 覆盖多个角度 | 对比/多条件查询 |

**集成方式：**
- 改写后的查询用于检索
- 原始问题用于生成回答
- 多个改写查询的结果去重融合

**改写对检索的影响（实验发现）：**
- 口语化问题（"X100能下水不？"）→ 扩展为"防水等级"显著提升检索
- 精确问题（"退款政策是什么"）→ 改写收益不大
- 对比问题（"X100和R50区别"）→ 拆解为子问题覆盖更全

### 4. 评估指标：用数字衡量检索质量

**三大核心指标：**

| 指标 | 含义 | 公式 | 特点 |
|------|------|------|------|
| Hit Rate@K | Top-K 中命中相关文档的比例 | hits / total_queries | 简单直观 |
| MRR | 第一个相关文档排名的倒数均值 | Σ(1/rank_first) / N | 考虑了排名 |
| nDCG@K | 综合排名+相关性程度的归一化指标 | DCG/IDCG | 最全面 |

**指标选择建议：**
- 快速验证：Hit Rate（够用了）
- A/B 对比：nDCG（最公平）
- 前端展示：MRR（用户只关心第一个）

**实验发现：**
- 在 9 篇文档小规模测试集上，三种策略 Hit Rate 都是 100%
- BM25 延迟最低（~650ms），纯向量最慢（~3340ms，因为 embedding 生成）
- Hybrid 在延迟和效果之间取得平衡（~1660ms，nDCG=0.9852）
- BM25 在小规模精确查询场景意外地好，但在语义模糊场景会拉胯

## 🔍 关键发现

### 发现 1：BM25 在小数据量精确查询场景出奇地好

在 9 篇文档、10 个测试查询的评估中，BM25 的 nDCG 达到 1.0：
- 每个查询都完美命中预期文档
- 延迟最低（~650ms，不需要 embedding）
- 原因：测试查询都包含精确关键词（"X100"、"退款"、"充电"）

**但这不代表 BM25 总是更好。** 在大规模数据（>1000 文档）中，语义模糊的查询会暴露 BM25 的局限性：
- "手机坏了怎么修" → BM25 可能找不到"产品保修"（没有精确匹配"坏了"）
- "员工看病报销" → BM25 找不到"公司医疗福利"（关键词不匹配）

⚠️ **评估偏差警示**：测试集太小（9 篇文档 10 个查询），评估结果不能代表生产环境。真正的评估需要 100+ 文档和 50+ 查询。

### 发现 2：Reranker 用 LLM 做评分成本高

用 GLM-4-Flash 做 10 次 rerank（每次 5 篇候选 = 50 次 LLM 调用）：
- 每次 ~500ms，总计额外 ~25 秒延迟
- 在小数据量场景不划算
- 生产环境应该用轻量级 Cross-Encoder（如 BGE-Reranker-v2-minicpm）

### 发现 3：ChromaDB 并发创建 collection 有竞争

- 多个 `PersistentClient` 同时创建/删除同一 collection 会触发 NotFoundError
- 解决方案：每个 evaluator 用不同的 collection name
- 生产环境应统一用单例模式管理 ChromaDB 客户端

### 发现 4：评估体系是工程化的基石

没有量化指标之前，我们靠"感觉"判断检索好坏。有了评估体系之后：
- 可以客观对比不同策略
- 可以放心做 A/B 实验
- 可以用数据说服别人"这个改进值得上线"

## ⚠️ 踩坑记录

### 1. rank_bm25 需要 tokenized 输入

**问题**：`BM25Okapi()` 接收的是字符串列表会报错，它需要已经 tokenized 的列表。
**解决**：先用 `tokenize_chinese()` 分词，再传入。

### 2. 中文分词的 separator 配置

与 Week 2 同样的坑——默认空格分句对中文无效。字符级切分虽然粗糙但够用，生产环境用 jieba。

### 3. RRF 实现要注意排名映射

两个检索器返回的 doc 可能不同（ID 对不齐），需要用 doc_index 在统一列表上计算排名，而不是简单地把两个结果列表拼接。

### 4. ChromaDB PersistentClient 多实例冲突

`make_search_fn` 被调用多次时，每个都创建新的 `PersistentClient` 访问同一个目录，collection 名称冲突导致 `NotFoundError`。修复方法：每评估器用唯一的 collection name。
