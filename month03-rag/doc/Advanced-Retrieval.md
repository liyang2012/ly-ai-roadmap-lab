# 高级检索策略科普

> 配套 Week 3 内容。Week 1/2 用的是纯向量检索，这篇介绍如何让检索更准确。

---

## 1. 为什么纯向量检索不够？

Week 1 和 Week 2 我们用的是 ChromaDB 的纯向量检索：把问题变成向量，找最相似的文档。

这种方式擅长理解语义（"坏了" ≈ "故障"），但有明显的短板：

### 短板 1：精确关键词匹配差

```
用户问："X100 的电池多大？"
向量检索可能返回：
  1. "R50 电池 5000mAh"  ← 语义相关但不是 X100！
  2. "X100 Pro Max 规格"  ← 正确但排名不是第一
```

向量检索理解"电池"的意思，但对"X100"这个精确型号的区分度不够。

### 短板 2：对专有名词、缩写不敏感

```
"Wi-Fi 7" vs "Wi-Fi 6"  → 向量几乎一样（都是网络协议）
"LPDDR5X" vs "LPDDR4X"  → 向量几乎一样（都是内存类型）
```

但这两个是完全不同的规格！

### 解决方案：混合检索

**向量检索**擅长语义理解 + **BM25 关键词检索**擅长精确匹配 = 取长补短。

## 2. BM25：经典的关键词检索算法

### 它是什么？

BM25 是搜索引擎领域最经典的算法之一（1994 年提出），Google 早期的核心排序算法。

简单来说，BM25 就是一个"更聪明的关键词匹配"：

| 特性 | 简单关键词匹配 | BM25 |
|------|-------------|------|
| 核心思想 | 统计相同词的数量 | 统计词频 + 考虑文档长度 + 考虑词的稀有度 |
| "的""是"等常见词 | 和重要词同等权重 | 自动降低权重（IDF） |
| 长文档 vs 短文档 | 长文档天然得分高 | 自动做长度归一化 |

### BM25 的核心思想

```
BM25 分数 = IDF（词有多稀有）× TF（词在文档中出现几次）× 长度归一化

- IDF：如果一个词在所有文档中都出现（如"的"），它的 IDF 值很低
       如果一个词只在少数文档中出现（如"X100"），它的 IDF 值很高
- TF：词在目标文档中出现越多，分数越高
- 长度归一化：避免长文档因为"词多"而天然占优势
```

### 向量和 BM25 的对比

| 问题类型 | 向量检索 | BM25 |
|---------|---------|------|
| 语义相似（"坏了"≈"故障"） | ✅ 优秀 | ❌ 弱 |
| 精确关键词（"X100"型号） | ❌ 不稳定 | ✅ 强 |
| 同义词（"免邮"="包邮"） | ✅ 好 | ❌ 差 |
| 缩写/代码（"R50"） | ⚠️ 一般 | ✅ 好 |
| 中文口语（"能下水不"） | ✅ 好 | ❌ 差 |

## 3. Hybrid Search：向量 + BM25 = 取长补短

### 工作原理

```
用户问题："X100手机屏幕坏了怎么办？"
        │
        ├──→ 向量检索 (ChromaDB)     → [保修政策, 物流配送, ...]
        │       语义：理解"坏了"="故障"
        │
        └──→ BM25 关键词检索          → [X100说明书, 保修政策, ...]
                关键词：精确匹配"X100"
        │
        ▼
    融合排序 → 综合两个列表，找出最终排名
```

### RRF 融合算法（Reciprocal Rank Fusion）

两个检索各返回一个排序列表，怎么合并？

**RRF 的核心思想**：在两个列表中都排前面的文档，最终得分应该最高。

```
RRF_score(文档) = 1/(k + 向量排名) + 1/(k + BM25排名)

k = 60（平滑参数，防止排名 1 的文档权重过大）
```

**举个例子**：

| 文档 | 向量排名 | BM25排名 | RRF 得分 |
|------|---------|---------|---------|
| 保修政策 | 1 | 2 | 1/(60+1) + 1/(60+2) = 0.0164 + 0.0161 = **0.0325** |
| X100说明书 | 5 | 1 | 1/(60+5) + 1/(60+1) = 0.0154 + 0.0161 = **0.0315** |
| 物流配送 | 2 | 8 | 1/(60+2) + 1/(60+8) = 0.0161 + 0.0147 = **0.0308** |

→ 保修政策在两个列表都靠前，最终排第一 ✅

### alpha 参数控制权重

我们的实现中用 `alpha` 参数控制两种检索的比重：

```python
alpha = 0.5  # 各占一半（默认推荐）
alpha = 1.0  # 纯向量检索（等于 Week 1）
alpha = 0.0  # 纯 BM25
alpha = 0.7  # 偏重语义（口语化查询多时用）
alpha = 0.3  # 偏重关键词（精确查询多时用）
```

## 4. Reranking：精排的最后一步

### 为什么需要 Reranking？

向量检索和 BM25 都是"快速初筛"——它们需要很快地从几千篇文档中找出候选。

但"快"意味着"精度有限"。Reranking 是第二遍精细排序：

```
第 1 步：快速初筛 → 20 篇候选（用向量/BM25，速度快，精度一般）
第 2 步：精细排序 → 5 篇最终（用 Reranker，速度慢，精度高）
第 3 步：LLM 基于这 5 篇生成回答
```

### Bi-Encoder vs Cross-Encoder

| 方面 | Bi-Encoder（向量检索用的） | Cross-Encoder（Reranker 用的） |
|------|------------------------|------------------------------|
| 编码方式 | 问题和文档分别编码 | 问题和文档一起编码 |
| 速度 | 快（文档向量可预计算） | 慢（每对都要重新算） |
| 精度 | 中等 | 高 |
| 使用阶段 | 初筛（从几千篇找 20 篇） | 精排（从 20 篇找 5 篇） |

**类比**：
- Bi-Encoder 像"看简历筛选"——快速浏览，每人 30 秒
- Cross-Encoder 像"面试"——深入交流，每人 30 分钟

### LLM Reranker（我们用的简化方案）

为了让原理更直观，我们用 LLM 来做 Reranking：

```python
# 对每个候选文档，让 LLM 评估相关性
prompt = f"""请评估以下文档与用户问题的相关性，返回 0 到 1 的分数。

用户问题：{query}
文档内容：{doc_text}

相关性分数："""
```

**注意**：这只是教学演示。生产环境应该用专门的 Cross-Encoder 模型（如 BGE-Reranker-v2-minicpm），速度更快、成本更低。

### 实验发现

用 LLM 做 Reranking 的成本：
- 每个文档对 ~500ms
- 10 次查询 × 5 篇候选 = 50 次 LLM 调用
- 总延迟增加 ~25 秒

在小数据量场景不划算。但如果你处理的是 1000+ 文档，Reranking 的价值就体现出来了。

## 5. Query 改写：让检索更聪明

### 为什么需要改写？

用户的提问方式和文档的表述方式经常不一致：

```
用户说："X100 能下水不？"
文档写："X100 支持 IP68 防水等级"
→ "下水" ≠ "防水等级"，向量检索可能不准
```

### 三种改写策略

#### 策略 1：关键词提取

把口语化的问题压缩成核心关键词：

```
原始："X100手机的防水等级是多少？能不能戴着游泳？"
改写："X100 防水等级 IP68 游泳"
→ 去掉了"的""是多少""能不能戴着"等噪声词
```

#### 策略 2：同义词扩展

生成文档中可能使用的正式表达：

```
原始："X100 能下水不？"
改写："X100 防水等级 IP68 水下工作 游泳佩戴"
→ 加入了文档中可能出现的同义词
```

#### 策略 3：子问题拆解

把复杂问题拆成多个可以独立回答的子问题：

```
原始："X100 和 R50 哪个更值得买？"
拆解：
  1. "X100 的规格和价格"
  2. "R50 的规格和价格"
  3. "X100 和 R50 对比"
→ 对每个子问题分别检索，结果合并去重
```

### 改写对检索的影响

| 问题类型 | 改写收益 | 原因 |
|---------|---------|------|
| 口语化问题 | 高 | 用词差异大，改写后匹配更准 |
| 精确问题 | 低 | 本来就能直接匹配 |
| 对比问题 | 中 | 拆解后覆盖更全面 |

### 关键设计

**改写只用于检索，原始问题用于生成回答**。

因为用户期望的回答是针对原始问题的——改写只是为了让检索更准，不应该改变 LLM 理解的问题本身。

## 6. 评估指标：用数字衡量检索质量

### 为什么需要评估？

之前我们都是"凭感觉"判断检索好不好。有了评估指标后，可以：
- 客观对比不同策略（向量 vs Hybrid vs Reranking）
- 调整参数后量化效果变化
- 用数据说服团队"这个改进值得上线"

### 三大核心指标

#### Hit Rate（命中率）— 最简单

```
Hit Rate@K = 在 Top-K 结果中至少命中 1 篇相关文档的查询比例

例：10 个查询中有 9 个在 Top-5 命中了相关文档
Hit Rate@5 = 9/10 = 90%
```

**优点**：简单直观
**缺点**：只看"有没有"，不看"排第几"

#### MRR（平均倒数排名）— 考虑排名

```
MRR = 所有查询的"第一个相关文档排名倒数"的平均值

例：
  查询 1：第 1 名就命中 → 1/1 = 1.0
  查询 2：第 3 名才命中 → 1/3 = 0.33
  查询 3：第 2 名命中   → 1/2 = 0.5
MRR = (1.0 + 0.33 + 0.5) / 3 = 0.61
```

**优点**：考虑了排名位置
**缺点**：只看第一个命中的文档

#### nDCG（归一化折损累计增益）— 最全面

```
nDCG 同时考虑：
1. 相关文档排在前面还是后面（排名越前分越高）
2. 相关文档的相关性程度（3 分 > 2 分 > 1 分）
3. 和"理想排序"对比，归一化到 0~1

nDCG = 1.0 表示完美排序
nDCG = 0.0 表示完全乱排
```

**优点**：最全面的评估指标
**缺点**：需要人工标注每篇文档的相关性分数

### 指标选择建议

| 场景 | 推荐指标 | 原因 |
|------|---------|------|
| 快速验证 | Hit Rate | 够用了 |
| A/B 对比 | nDCG | 最公平 |
| 前端展示 | MRR | 用户只关心第一个结果 |

## 7. 实验结果摘要

在我们的 9 篇文档 + 10 个测试查询的小实验中：

| 策略 | Hit Rate | MRR | nDCG | 平均延迟 |
|------|---------|-----|------|---------|
| 纯向量 (α=1.0) | 100% | 1.0 | 1.0 | ~3340ms |
| Hybrid (α=0.5) | 100% | 1.0 | 0.985 | ~1660ms |
| 纯 BM25 (α=0.0) | 100% | 1.0 | 1.0 | ~650ms |
| Hybrid + Rerank | 100% | 1.0 | ~0.98 | ~25000ms |

**关键发现**：
- 在小数据量 + 精确查询场景，BM25 意外地好（延迟最低，准确率 100%）
- 但这不代表 BM25 总是更好——大规模数据 + 语义模糊查询时，向量检索的优势才会体现
- 测试集太小（9 篇 10 查询），评估结果不能代表生产环境
