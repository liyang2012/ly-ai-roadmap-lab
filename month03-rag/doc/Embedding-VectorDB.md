## 1. Embedding：把文字变成"语义指纹"

### 核心概念

**Embedding（嵌入）** 就是把一段文字变成一串数字（向量），使得语义相似的文字对应的向量也"距离接近"。

```
"Python 怎么创建字典？"  → [0.123, -0.456, 0.789, ..., 0.012]  （2560 个数字）
"如何使用 dict 类型？"    → [0.118, -0.443, 0.801, ..., 0.015]  （和上面很接近！）
"今天天气怎么样？"        → [0.001, 0.892, -0.234, ..., 0.678]  （和上面差很远）
```

### 为什么这很厉害？

传统方法（关键词匹配）只看字面：
- "汽车" 和 "轿车" → 字面完全不同 → 匹配失败

Embedding 看语义：
- "汽车" → 向量 A
- "轿车" → 向量 B
- A 和 B 在高维空间中"距离很近" → 系统知道它们说的是类似的东西

### 类比理解

把 Embedding 想象成给每段文字打一个"语义条形码"：

| 文字 | 语义条形码（简化示意） |
|------|---------------------|
| "猫" | `[动物:0.9, 交通:0.1, 食物:0.2]` |
| "狗" | `[动物:0.85, 交通:0.15, 食物:0.25]` |
| "汽车" | `[动物:0.1, 交通:0.9, 食物:0.05]` |

猫和狗的条形码很像（都是动物），和汽车的条形码差别很大。

**注意**：真实的 Embedding 是 2560 个数字（维度），远比上面的 3 维复杂。每一维代表的"语义特征"是模型自己学出来的，人类无法直观解释。

## 2. 余弦相似度：衡量两个向量"有多像"

### 为什么需要它？

有了 Embedding 后，每段文字都变成了一串数字（向量）。我们需要一种方法来比较两串数字有多"接近"。

### 计算方法

**余弦相似度**（Cosine Similarity）是最常用的方法：

```
cos(θ) = (A·B) / (|A| × |B|)

取值范围：-1 到 1
  1.0 = 方向完全相同（语义完全一样）
  0.0 = 方向垂直（完全不相关）
 -1.0 = 方向完全相反（语义相反）
```

### 经验值参考

| 相似度范围 | 含义 | 举例 |
|-----------|------|------|
| > 0.8 | 高度相关 | "猫" ↔ "小猫" |
| 0.5 ~ 0.8 | 中度相关 | "猫" ↔ "狗" |
| 0.3 ~ 0.5 | 弱相关 | "猫" ↔ "宠物食品" |
| < 0.3 | 不相关 | "猫" ↔ "股票市场" |

### 直觉理解

把向量想象成从原点出发的箭头：
- 两个箭头指向同一个方向 → 相似度高（接近 1）
- 两个箭头指向不同方向 → 相似度低（接近 0）

## 3. Embedding 模型对比

不同的模型有不同的特点，选对模型很重要：

| 模型 | 维度 | 语言支持 | 运行方式 | 费用 | 推荐度 |
|------|------|---------|---------|------|--------|
| `all-MiniLM-L6-v2` | 384 | 仅英文 | 本地 ONNX | 免费 | ❌ 中文别用 |
| `text-embedding-3-small` | 1536 | 多语言 | OpenAI API | 按量付费 | ⭐⭐⭐⭐ |
| `qwen3-embedding:4b` | 2560 | 中文优化 | 本地 Ollama | 免费 | ⭐⭐⭐⭐⭐ |

### 关键发现：中文场景必须用中文模型

ChromaDB 默认的 `all-MiniLM-L6-v2` 是英文模型，对中文几乎无效：

```
使用英文模型：
  "什么是不可变的序列？" → 检索结果：随机乱排 ❌
  "怎么去除重复？"       → 检索结果：完全错误 ❌

切换为中文模型（qwen3-embedding:4b）：
  "什么是不可变的序列？" → 检索结果：正确找到元组文档 ✅
  "怎么去除重复？"       → 检索结果：正确找到集合文档 ✅
```

**结论**：Embedding 模型的语言能力是 RAG 质量的基础。中文场景一定要用中文优化的模型。

## 4. 向量数据库：专门存储和检索"语义指纹"的数据库

### 为什么不用普通数据库？

传统数据库（如 MySQL）擅长精确查询：
```sql
SELECT * FROM docs WHERE title = 'Python教程'
```

但它做不了语义查询：
```sql
-- 这种查询 MySQL 做不到！
SELECT * FROM docs WHERE meaning ≈ '怎么创建字典'
```

向量数据库就是为了解决这个问题：它能快速找到"语义最接近"的文档。

### ChromaDB：我们选择的向量数据库

ChromaDB 是一个开源的向量数据库，专为 AI 应用设计。它的特点：

| 特点 | 说明 |
|------|------|
| 简单易用 | API 设计友好，5 分钟上手 |
| 自带 Embedding | 可以自动生成向量，不需要手动调用 |
| 持久化 | 数据可以保存到磁盘，重启不丢失 |
| 元数据过滤 | 可以按条件先过滤，再做向量检索 |

### ChromaDB 的数据结构

```
Client（数据库连接）
  └── Collection（类似 SQL 的"表"）
        ├── Document（文档的文本内容）
        ├── Embedding（文档的向量，自动生成）
        ├── Metadata（附加信息：来源、日期、分类等）
        └── ID（唯一标识，用于定位文档）
```

### 五大核心操作

```python
# 1. 添加文档（CREATE）
# 只要给文本，ChromaDB 会自动生成向量
collection.add(
    documents=["Python 的列表是有序可变序列"],
    ids=["doc1"],
    metadatas=[{"topic": "list", "difficulty": "basic"}]
)

# 2. 语义查询（QUERY）— 最核心的操作！
# 给一个问题，ChromaDB 自动找到最相似的文档
results = collection.query(
    query_texts=["怎么创建列表？"],  # 会自动变成向量
    n_results=2,                     # 返回最相似的 2 个
)
# 返回的 distance（距离）越小越相关：
#   0.0 ~ 0.3：非常相关
#   0.3 ~ 0.6：高度相关
#   0.6 ~ 1.0：有一定相关性
#   > 1.0：不太相关

# 3. 按 ID 获取（GET）
result = collection.get(ids=["doc1", "doc2"])

# 4. 更新文档（UPDATE）
collection.update(ids=["doc1"], documents=["新内容"])

# 5. 删除文档（DELETE）
collection.delete(ids=["doc1"])
```

### 两种运行模式

| 模式 | 用法 | 数据保存 | 适用场景 |
|------|------|---------|---------|
| 内存模式 | `Client()` | 程序结束就消失 | 测试、演示 |
| 持久化模式 | `PersistentClient(path="./data")` | 保存到磁盘 | 生产环境 |

**什么时候需要持久化？**
- 5 篇文档：索引 ~1 秒，不需要持久化
- 100 篇文档：索引 ~10 秒，建议持久化
- 1000 篇文档：索引 ~100 秒，必须持久化

### 元数据过滤：先筛选再检索

假设你的知识库里有产品文档和 HR 文档，你可以先按类别过滤：

```python
# 只在产品文档中搜索
results = collection.query(
    query_texts=["X100 防水等级"],
    n_results=3,
    where={"category": "product"}  # 先过滤，再向量检索
)
```

这在大规模知识库中非常有用——先缩小范围，再精确检索。

## 5. 向量数据库的内部原理（选读）

ChromaDB 底层使用 **HNSW**（Hierarchical Navigable Small World）算法进行近似最近邻搜索。

### 为什么不用暴力搜索？

最直接的方法是：把查询向量和每个文档向量都算一遍相似度，然后排序。

但这在大规模数据下太慢了：
- 1000 篇文档：1000 次计算，可以接受
- 100 万篇文档：100 万次计算，太慢了

HNSW 通过构建"图"结构，只需要访问少量节点就能找到近似最优解。

### 距离计算方式

ChromaDB 支持三种距离计算：

| 方式 | 配置 | 值域 | 特点 |
|------|------|------|------|
| cosine（余弦） | `hnsw:space: "cosine"` | 0~2 | 我们用的，0=完全相同 |
| l2（欧氏距离） | `hnsw:space: "l2"` | 0~∞ | 空间中的直线距离 |
| ip（内积） | `hnsw:space: "ip"` | -∞~∞ | 越大越相似（注意方向相反）|

## 6. 实践中的注意事项

### Ollama 服务配置

我们使用本地 Ollama 运行 Embedding 模型：

```bash
# 1. 确保 Ollama 正在运行
ollama serve

# 2. 下载中文 Embedding 模型（首次需要）
ollama pull qwen3-embedding:4b

# 3. API 地址
# POST http://localhost:11434/api/embed
# Body: {"model": "qwen3-embedding:4b", "input": "要转换的文字"}
```

### ChromaDB 首次运行的"坑"

第一次使用 ChromaDB 时，它会自动下载默认的英文模型 `all-MiniLM-L6-v2`（79MB），即使你用的是 Ollama 中文模型。这是正常行为，不用担心。

下载位置：`~/.cache/chroma/onnx_models/`

### 依赖安装

```bash
pip install chromadb    # 向量数据库
pip install ollama      # Ollama Embedding 函数的依赖
pip install numpy       # 余弦相似度计算
```
